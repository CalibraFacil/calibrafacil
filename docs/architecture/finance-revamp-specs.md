# Financeiro revamp — implementation specs (from spec workflow)

Generated by the `financeiro-revamp-specs` multi-agent workflow (7 surface
designers + 1 consistency critic). Companion to `finance-revamp.md`. This is the
execution reference for Waves 1e–5; treat the build order + shared-file rules as
authoritative to avoid clobbering append-only registries.

## Build order (critic)

1. **Wave 1b: targeted-invalidation mutations.ts (finance/mutations.ts)** — MUST build first as all other waves depend on optimized mutation patterns. Establishes the onMutate snapshot + setQueryData pattern centrally. Fixes the Conta Azul 'lag' root cause (broad prefix invalidations). Independent of other features.
1. **Wave 1b: Conta Azul lag/bug fixes (Wave 1c spec)** — Depends on mutations.ts. Fix broad invalidations, add per-target optimistic sync state (conta-azul-sync-state.ts), surface errors inline on buttons. Can ship early and unblock PR #333 merge independently. Removes integrations-page.tsx catalog band-aid.
1. **Wave 1a: shared primitives (finance-data-table, inline-edit-field, preview-drawer pattern)** — Build once, reused by Receivables (Wave 1e), Contracts (Wave 2), Analytics (Wave 3), Document detail (Wave 4). finance-data-table wraps ui/data-table.tsx with row selection + bulk-action bar + faceted filter state. inline-edit-field is keyed-remount pattern for DRAFT edits. No external dependencies beyond ui/* primitives.
1. **Wave 1e: Receivables Workspace** — Consumes finance-data-table, inline-edit-field. Implements ReceivablesPage + FinanceDataTable + ReceivablesPreviewDrawer + InlineReceiptForm + ReceivablesFilters. Updates route-meta.ts (add receivables nav), queries.ts (no new queries, compose listDocuments+listReceipts client-side), types.ts (row-keying for installment/document pairs). Creates features/finance/mutations.ts with receiveInstallment optimistic pattern.
1. **Wave 2: Contracts Redesign** — Depends on shared primitives + mutations.ts. Creates features/finance/forms.ts (schema-first contract validation), features/finance/service-terms-editor.tsx (reusable, exported), features/finance/contracts-list-data-table.tsx, features/finance/contract-preview-drawer.tsx, features/finance/contract-detail-page.tsx redesign, features/finance/new-contract-page.tsx refactor. Updates route-meta.ts (if adding filters), queries.ts (adds service/customer option lookups), types.ts (contract tone mapper). Removes 'Condições comerciais' duplication.
1. **Wave 2: Automação page** — Independent from other waves (pure UI wrapper around existing backend). Creates features/finance/automation/ subdirectory with automation-page.tsx, certificate-release-tab.tsx, automatic-send-tab.tsx, forms.ts (validation only), queries.ts (list endpoints). Updates route-meta.ts (add /dashboard/finance/automation to nav), redirects if old /settings/certificate-release URL exists.
1. **Wave 3: Analytics Hub** — Depends on Receivables drill-down support (URL filters ?stage= ?leakageClass= ?customer=). Creates features/finance/analytics-hub-page.tsx + 4 card components. Updates route-meta.ts (add /dashboard/finance/analytics), analytics-page.tsx (if it exists, add drill-down Link components). Receivables list must support URL search param filtering (frontend-only for Wave 3, server-side filtering flagged Wave 3.5).
1. **Wave 4: Document Detail Timeline Redesign** — Depends on mutations.ts + inline-edit-field. Creates components/ui/inline-edit-field.tsx (if not already in primitives wave), features/finance/document-timeline.tsx, features/finance/mutations.ts extension (update/issue/void/export mutations). Refactors features/finance/document-detail-page.tsx to use Panel layout + Timeline. No route changes, no types.ts changes (reuses BillingDocumentDetails).
1. **Wave 5: new-document + new-contract forms** — Depends on service-terms-editor (Wave 2), mutations.ts, forms.ts validation. Creates features/finance/eligible-jobs-table.tsx, refactors features/finance/new-document-page.tsx (mode-switch confirmation + live discount summary + EligibleJobsTable), refactors features/finance/new-contract-page.tsx (ServiceTermsEditor reuse + single Condições section). Creates features/finance/forms.ts if not already done in Wave 2. No new routes, no new queries (reuses financeEligibleJobsQueryOptions).

- Navigation structure (route-meta.ts) not fully defined: Spec assumes receivables, automation, analytics are added to Finance subnav. Verify final nav order in finance-revamp.md (table on line 44-54 shows desired structure). Implement redirects for old /documents and /receipts URLs in Wave 1e.

Establish clear query key hierarchy across mutations.ts (onSuccess setQueryData keys must match queries.ts exports). Recommend: ['finance', 'category', 'id-or-search'] pattern consistently.
- Analytics enums (CashForecastBucket, OperationsStageName, LeakageClassName, etc.): Specs reference these but not defined in types.ts. Move from existing analytics pages to shared finance/analytics/types.ts or keep inline if Wave 3 only. Ensure Wave 3 analytics cards have complete enum definitions before shipping.
- Automation backend response shape (PolicyDTO, RuleDTO): Specs assume these exist in Wave 2 Automação, but current codebase shows certificate-release.tsx already in finance/. Verify backend endpoints return expected shapes (PolicyDTO with { id, mode, customerId, scope, priority, archivedAt, ... }). If fields differ, adjust Wave 2 component data flow.
- Receivables row keying strategy: Spec shows one row per installment (not per document). Key must be (documentId, installmentId) to enable bulk selection and filtering. Verify that receivables-data-table column definitions handle this keying (potential edge case: if multiple installments from one document are selected, must deduplicate documentId for bulk export/issue).
- Service/Unit name resolution in contract detail: Spec notes opaque IDs in service terms (serviceId, unitId). Wave 2 must fetch service/unit names via separate lookups. Backend should ideally denormalize these names into contract detail response (Wave 2 server ask). Until then, implement frontend LEFT JOIN via prewarmed options queries.
- Mutation rollback UX: Specs assume optimistic state persists until server response or error. If mutation fails, error toast shown and data rolled back. Verify React Query's onError rollback logic is correct (especially for nested detail/list patches). Test race conditions (user mutates, immediately navigates away).
- Form validation (schema-first): Specs assume @calibra-facil/schemas provides CreateContractInput, CreateDocumentInput schemas. Verify these exist or define locally in forms.ts. If not in shared, Wave 2 Contracts must define schema inline.
- Keyed remount pattern enforcement: Specs rely on keyed remount for form resets (e.g., document-detail PreviewDrawer key={docId}). Verify no-use-effect.mjs linter is configured to allow this pattern (or flag-list it). Ensure CI passes.
- Finance-scoped module hierarchy: Specs create subdirectories (automation/, analytics/, console/). Verify import paths are clear (features/finance/automation/automation-page.tsx, not buried). Ensure lazy loading of analytics pages doesn't break code-splitting expectations.

- Error state surfacing (Conta Azul lag fix): Wave 1c adds per-target sync state (pending, error). Verify RemoteStatusPollResult shape from backend includes warnings[] array. If not, adjust mutation success handler to extract error info.
- CurrencyInput component status: Spec assumes CurrencyInput exists in components/ui/currency-input.tsx. Verify it's implemented with controlled valueCents prop and onValueChange callback. If not, create in Wave 1a as shared primitive.
